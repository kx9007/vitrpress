# 前端性能优化：先测量，再优化

性能优化最常见的错误，是还没测量就动手。上来就加 `loading="lazy"`、拆包、上 CDN，一通操作下来指标没啥变化，因为你优化的可能根本不是瓶颈。

## 先定义"慢"

"页面慢"是个感受，不是指标。要优化，先把它变成一个数：

- **LCP**（Largest Contentful Paint）：主要内容多久出现
- **INP**（Interaction to Next Paint）：点了多久有反应
- **CLS**（Cumulative Layout Shift）：内容会不会乱跳

这三个是 Core Web Vitals 的核心。先测出基线，再谈优化。

## 怎么测

本地用 Lighthouse 快速看个大概，但**不要只信本地**。真实用户数据（RUM）才反映真实情况：

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.name, entry.startTime)
  }
}).observe({ type: 'largest-contentful-paint', buffered: true })
```

本地开发机性能好、网络快，往往测不出问题。用户在地铁里用 4G 打开你的页面，那才是真实场景。

## 一个真实的排查过程

有次一个列表页 LCP 是 4.2 秒，团队第一反应是"图片太大"，于是压图、上 CDN、加懒加载。结果只降到 3.9 秒。

后来老老实实看了一遍瀑布图，发现问题在别处：

1. 页面先请求了一个 300KB 的字体文件（`font-display` 没设）
2. 字体阻塞了首屏文本渲染
3. 图片其实加载得挺快

改成 `font-display: swap` + 字体子集化之后，LCP 直接降到 1.8 秒。

**如果一开始就测量，这两个小时能省下来。**

## 优化的优先级

按投入产出比排序，我一般这么做：

### 1. 减少关键路径上的字节

首屏需要的 CSS/JS 越小越好。用构建工具分析产物，看看是不是把整个 UI 库都打进去了。

```bash
npx vite-bundle-visualizer
```

### 2. 字体和图片

- 字体：子集化 + `font-display: swap` + 预加载关键字体
- 图片：现代格式（AVIF / WebP）+ 正确的尺寸 + 首屏图不要懒加载

### 3. 缓存策略

静态资源用内容哈希命名，配 `Cache-Control: max-age=31536000, immutable`。HTML 不缓存或短缓存。这一条改完，二次访问的体验会有质变。

### 4. 代码分割

路由级分割基本是标配了。但注意别过度分割——请求太碎反而更慢，因为每个请求都有开销。

## 不要做的事

**不要为了指标而优化指标。** 把 LCP 从 1.2 秒优化到 1.0 秒，用户感知不到，但你花了一周。

**不要盲目上 SSR。** 很多内容型页面用静态生成就够了，SSR 带来的是运维复杂度。

**不要在没数据的时候做决策。** "我觉得这里慢"不是理由，"这里耗时 800ms 占了首屏的 40%"才是。

## 小结

性能优化的顺序永远是：**测量 → 找瓶颈 → 改一处 → 再测量**。

跳过第一步，后面全是猜。
